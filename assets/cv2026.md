## One-liner (elevator)

Built a natural-language intelligence assistant that lets analysts query a 90+ table legacy
database in plain Spanish — "what did person X do in June 2022?", "shared events between X and Y",
"all incidents at facility Z in 2025" — combining **deterministic SQL retrieval (RAG)** with a
**100% local LLM** for grounded, citation-backed narrative reports. Zero hallucinated facts,
zero data egress, runs on CPU-only hardware.

---

## The problem it solves (business value)

- Analysts previously had to manually cross-reference dozens of tables to reconstruct a person's
  history or find links between individuals. Slow, error-prone, expert-only.
- The chatbot turns a multi-step manual investigation into a **single natural-language question**,
  returning a structured, sourced report in seconds.
- Runs entirely **on-premise / air-gapped** — mandatory for classified PII (no cloud LLM, no data
  leaving the network).

## Impact (quantify with real numbers before publishing)

- Reduced a typical cross-reference investigation from **~minutes of manual DB work to one query**.
- Covers **90+ legacy modules** and **two databases** (legacy + operational) in a single answer.
- **0 hallucinated facts** by design (retrieval is deterministic SQL; the LLM only narrates
  already-retrieved records).
- Runs on **CPU-only** hardware (~1 GB model), no GPU budget required.

## Key techniques (the interesting engineering)

**1. Structured RAG (SQL-RAG), not vector search**
Retrieval is deterministic, parameterized SQL over a whitelisted schema registry — exact results,
no embeddings, near-zero RAM. Chose this over pgvector/embeddings because the data is highly
structured and hallucinated IDs/dates are unacceptable in an intelligence context.

**2. Grounded generation with a local LLM**
A small local model (Qwen2.5-1.5B via Ollama) only *narrates* records already fetched by SQL —
it never invents facts. Institutional-tone Spanish reports with strict anti-fabrication prompting.
Graceful degradation: if the LLM is down, users still get the deterministic table + PDF.

**3. Inline citations / attribution**
Each retrieved record is numbered; the model is instructed to cite `[n]` after every claim. The
frontend rewrites `[n]` into deep-links to the source record — auditability + anti-hallucination.

**4. LLM structured output / function-calling for NL parsing**
Free-text questions are parsed into a typed intent (`{intent, people[], module, filter, dates}`)
via JSON-mode LLM extraction, with a fast deterministic path for obvious cases (IDs, dates).
Robust to arbitrary phrasing, compound surnames, and Spanish month names.

**5. Multi-intent classification**
One chat surface routes three retrieval strategies: single-person history, two-person shared-events
("cross"), and filtered module listings — each with a confirm-before-run UX (the bot echoes who/what
it understood before querying).

**6. Token-streaming UX**
Narrative streams token-by-token over NDJSON (Ollama stream → FastAPI → NestJS proxy → browser),
with proxy buffering disabled end-to-end for real-time output on slow CPU inference.

**7. Query performance on legacy schema**
Person↔record links live in a bridge table; naive self-joins full-scanned (>45s timeout). Solved
by running two indexed single-entity queries and intersecting in application code, and by applying
`COLLATE` to the literal (not the column) to preserve the index. Sub-second results.

**8. Security / access control**
Backend allowlist gate (directors/intelligence only) mirrored in the frontend; sensitive endpoints
gated server-side. Bearer-token-authenticated internal AI microservice (browser never talks to the
model directly).

## Architecture (one sentence per layer)

- **Frontend:** Next.js 14 / React / TypeScript — chat widget, disambiguation UX, streaming render,
  PDF export.
- **Backend:** NestJS / Prisma — SQL-RAG retrieval, access gating, AI proxy with server-side bearer.
- **AI microservice:** Python / FastAPI — Ollama (local LLM) for parsing + grounded narrative,
  JSON-mode structured output, NDJSON streaming.
- **Data:** MariaDB (legacy + operational DBs), raw parameterized SQL over a whitelisted registry.

## Talking points (interview / behavioral)

- **Why SQL-RAG over embeddings?** Structured data + zero-hallucination requirement + no GPU/RAM
  budget → deterministic SQL beats vector search here. Shows judgment, not just following hype.
- **Constraint-driven design:** air-gapped, CPU-only, sensitive PII → every choice (local model,
  server-side gating, grounded-only generation) traces to a real constraint.
- **Graceful degradation:** LLM optional — deterministic tables/PDF always work; AI is an enhancement.
- **Trade-off owned:** small local model = fast + private but weaker reasoning → mitigated with
  strong retrieval + tight grounded prompts + citations instead of a bigger model.
